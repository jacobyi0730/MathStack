# 34. 성능 예산

> 이 게임은 화면에 적 수백 마리가 동시에 존재한다. **아래는 권고가 아니라 제약이다.**
> 가독성을 이유로 완화하지 않는다. 위반하면 리뷰에서 반려된다.

## 1. 예산

| 시나리오 | 기준 |
| --- | --- |
| 적 300체 + 투사체 200개 | 프레임 **16.6ms 이내** (60FPS) |
| 최악 프레임 (p99) | 33ms 이내 |
| GC 일시정지 | 프레임당 **0회** |
| 충돌 구간 | 6ms |
| 렌더 구간 | 4ms |
| 프레임당 신규 할당 (`pool alloc`) | **0** |

| 번들 | gzip 상한 |
| --- | --- |
| 게임 번들 | 100KB |
| 학년별 문항 뱅크 (각) | 150KB |

## 2. 게임 루프 규칙

1. **고정 타임스텝.** 시뮬레이션 1/60초 고정, 렌더는 분리. `dt`는 항상 **초 단위**이며 `0.25`초 상한을 건다(탭 복귀 시 폭주 방지).
2. **업데이트 루프 안에서 할당 금지.** `new`, 객체 리터럴, `map`/`filter`/스프레드로 배열을 새로 만들지 않는다. 벡터 연산은 결과 객체를 재사용한다.
3. **오브젝트 풀 필수.** 적·투사체·데미지 텍스트·파티클은 `src/engine/pool.ts`로 재사용한다. 매 프레임 생성/폐기 금지.
4. **충돌은 공간 해시로.** O(n²) 전수 비교 금지 (`src/engine/spatial-hash.ts`). 질의는 **결과 배열을 인자로 받아 채운다.**
5. **렌더는 배치로.** 같은 스프라이트끼리 모아 그리고, 화면 밖 오브젝트는 컬링한다.
6. **게임 루프에서 `await`·`fetch` 금지.** 런타임 서버가 없다. 문항 뱅크는 **게임 시작 전 1회** 로드해 메모리에 올리고, 이후 출제·채점은 전부 동기 함수다.
7. **DOM은 매 프레임 갱신하지 않는다.** HUD는 값이 바뀔 때만, 변동이 잦은 값은 10프레임에 1회로 스로틀한다.

## 3. 측정

측정 없이 "빨라졌다"고 말하지 않는다. 절차는 **`perf-check` 스킬**에 있다.

스트레스 모드(`?stress=1`)가 표시하는 값:

```
frame  12.4ms   sim 4.1  collide 5.2  render 3.1   entities 487  pool 0 alloc
```

`pool alloc`이 0이 아니면 루프 안에서 할당이 일어나고 있다. 즉시 원인을 찾는다.

## 4. 위반 시 점검 순서

프레임이 예산을 넘으면 **이 순서로** 의심한다. 대개 1~3에서 잡힌다.

1. **루프 안 할당** — `new`, 객체 리터럴, `map`/`filter`/스프레드
2. **오브젝트 풀 미사용** — 매 프레임 생성/폐기
3. **O(n²) 충돌** — 공간 해시 미사용, 또는 셀 크기 부적절
4. **컬링 누락** — 화면 밖을 그리고 있는가
5. **배치 미적용** — `fillStyle` 변경 횟수
6. **캔버스 상태 변경 과다** — `save`/`restore`

## 5. 최악 시나리오

**9:00~10:00 최종보스 구간**이 성능 최악이다. 잡몹 300체 + 오가네손 3페이즈 탄막 + 각성 무기 투사체가 겹친다. 여기서 프레임이 무너지면 게임의 클라이맥스가 망가진다. 스트레스 모드에 이 프리셋을 둔다.
